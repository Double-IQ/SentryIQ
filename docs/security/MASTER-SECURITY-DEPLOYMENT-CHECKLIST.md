- [x] **2.3** Audit XSS sinks, DOM insertion, templates, and output escaping.
  - Reviewed on `main`: `index.php`, `app/Vault/DashboardList.php`, `app/Vault/DashboardActions.php`, `documents.php`, `welcome.php`, `app/Auth/PasskeyLogin.php`, `app/Auth/PasskeySetup.php`, `gallery_b2_diagnostic.php`, `diagnostics/self_test.php`, `app/Gallery/SecurePage.php`, and the related Vault/Gallery browser assets (`records_view.js`, `vault_folders.js`, `gallery_secure_ui.js`, `gallery_secure.js`, `gallery_storage.js`, `gallery_crypto.js`).
  - Vault record-card output: record fields are serialized with `json_encode(..., JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT)` and then HTML-attribute encoded before use in the inline handler. This is context-safe against HTML/script breakout in the inspected path. Visible labels, usernames, category/folder values, form values, and passkey labels/IDs are HTML-escaped; query-derived category/folder values are constrained against the stored category/folder lists before rendering. The record detail UI uses `textContent` and validates destination links as HTTPS before assigning `href`.
  - Documents page: document names and IDs are HTML-escaped or constrained to the expected hexadecimal identifier format; the icon helper returns a fixed emoji allowlist; status messages are selected from fixed strings. No unescaped document metadata sink was identified in the inspected template.
  - Passkey and Gallery UI: inspected message/metadata insertion uses `textContent`, DOM element creation, and property assignment rather than parsing untrusted strings as HTML. Gallery filenames/albums are displayed through `textContent`; thumbnail/preview URLs are generated as object URLs from decrypted image bytes.
  - DOM HTML sinks found: `DashboardList.php` builds the System Tools panel with `innerHTML`, but the inserted markup is a fixed, developer-authored string with no user/config/request data; `vault_folders.js` assigns fixed option markup to `select.innerHTML`; `diagnostics/self_test.php` uses `innerHTML` for table rows and summary markup, with dynamic fields passed through its `esc()` HTML-escaping helper. No `eval`, `new Function`, or `document.write` sink was identified in the inspected browser assets.
  - **Hardening finding (not confirmed exploitable XSS):** `diagnostics/self_test.php` embeds `$browserTests` and `$results` into executable `<script>` blocks using `json_encode()` without `JSON_HEX_TAG` (and embeds `$csrf`/build metadata without a uniform script-data encoding helper). `$results` can include environment/configuration-derived strings, including the request Host value and configuration exception details. JSON string encoding alone does not neutralize a literal `</script>` for the HTML parser. This is a context-encoding weakness; exploitability depends on an attacker being able to influence one of those diagnostic values and induce an authenticated diagnostic request. Correct it by using a single script-context encoder with `JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT | JSON_THROW_ON_ERROR` for every PHP-to-JavaScript value, or move data into non-executable JSON with equivalent safe encoding. Add a regression test using a `</script><script>` payload in a controlled diagnostic value.
  - Context note: `htmlspecialchars()` defaults are used in a few older output expressions without explicit flags/charset, while newer adjacent expressions specify `ENT_QUOTES, 'UTF-8'`. PHP 8.3's defaults include quote escaping, so no concrete bypass was demonstrated, but standardize all HTML text/attribute output to explicit `ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8'` during remediation.
  - No application code or production configuration was changed during this audit. This item records the audit and the exact hardening target; the actual remediation is tracked as a follow-up implementation before CSP tightening. No confirmed exploitable XSS was established in the inspected paths.
- [x] **2.4** Audit CSRF protections on every state-changing action.
  - Audited `app/Security/SecurityBootstrap.php`, `index.php`, `app/Auth/AuthFlow.php`, `app/Auth/PasskeyAuth.php`, `app/Security/FirstRun.php`, Vault action handlers (`app/Vault/Actions.php`, `CategoryActions.php`, `RecordActions.php`), document handlers (`app/Documents/Upload.php`, `Delete.php`), Gallery settings/diagnostic handlers (`app/Gallery/Settings.php`, `gallery_b2_settings.php`, `gallery_b2_diagnostic.php`), and the retired Gallery server endpoints.
  - Central CSRF implementation: `sentryiq_csrf_token()` creates a 256-bit random hex token in the session. `sentryiq_require_csrf()` accepts POST only, supports form field or `X-CSRF-Token`, rejects missing/mismatched tokens with 403, and uses `hash_equals()`. The session cookie is configured `SameSite=Strict`, `HttpOnly`, and `Secure`; session IDs use strict mode. Authentication success regenerates the session ID and rotates the CSRF token.
  - Covered state-changing operations: password/recovery login steps and first-run completion call `sentryiq_require_csrf()`; vault add/edit/delete/category/settings/folder handlers call it; document upload/delete call it after authentication; Gallery settings save/disconnect call it and additionally require fresh authentication; Gallery B2 diagnostic `prepare` validates the session token manually before issuing short-lived B2 operation URLs; passkey register/delete validate the JSON request token manually with `hash_equals()` and require authentication. Vault lock POST validates CSRF in both the bootstrap lock hook and the index entry point. Legacy server-side Gallery upload/delete/album endpoints return 410 and do not mutate state.
  - Forms on the index page receive a token from the meta tag via the page initializer; explicit forms on first-run, Gallery, and B2 settings pages render a hidden token. Passkey browser requests carry the token in JSON. The B2 diagnostic fetch sends the token in JSON. No state-changing GET operation was identified in the inspected flows; passkey GET options endpoints only create short-lived session challenges and do not mutate account or stored application data.
  - Findings/limitations: (1) CSRF enforcement is not centralized automatically at the HTTP router; each handler must remember to invoke it. Current audited mutation handlers do so, but future endpoints need regression coverage. (2) Passkey register/delete and B2 diagnostic duplicate the token comparison instead of using one shared JSON-request verifier, creating drift risk. (3) The index page's automatic token injection depends on its JavaScript initializer; any newly introduced POST form on that page must include a token explicitly or be covered by the initializer. (4) The login passkey assertion POST does not use a CSRF token, but it is an unauthenticated login ceremony bound to a session challenge, WebAuthn origin/RP ID, and authenticator signature; no authenticated state-changing action is exposed through that operation.
  - No missing CSRF check was confirmed in the reviewed state-changing handlers. No application code or production configuration was changed; this is an audit result, not a remediation.
- [x] **2.5** Verify browser security headers, HTTPS behaviour, and cookie attributes.
  - Reviewed `app/Security/SecurityBootstrap.php`, `app/Gallery/SecurePage.php`, `gallery_b2_diagnostic.php`, `gallery_b2_settings.php`, and the root `.htaccess` / `.user.ini` files on `main`.
  - Central bootstrap emits `Cache-Control: no-store, no-cache, must-revalidate, max-age=0`, `Pragma: no-cache`, `Expires: 0`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()`, and a restrictive baseline CSP (`default-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'none'`, `form-action 'self'`; `img-src 'self' data:`). CSP still allows `unsafe-inline` for script/style, already recorded under 2.1/2.2.
  - HTTPS enforcement: non-CLI requests are rejected unless `$_SERVER['HTTPS'] === 'on'` or `SERVER_PORT === '443'`. This prevents ordinary direct HTTP requests, but relies on server-provided HTTPS/port values; reverse-proxy deployments must preserve a trustworthy HTTPS indicator. Do not trust arbitrary forwarded headers without a configured trusted-proxy boundary.
  - Session cookie: lifetime 0, path `/`, Secure, HttpOnly, SameSite=Strict; strict session mode and cookie-only sessions enabled. No explicit cookie domain is set, so the cookie remains host-only. Logout/lock expires the cookie using the active path/domain/Secure/HttpOnly attributes before destroying the session.
  - **Confirmed hardening gap:** no `Strict-Transport-Security` (HSTS) header is emitted by the central bootstrap or the inspected page-specific handlers/config files. Once the production hostname and all relevant subdomains are confirmed HTTPS-only, add HSTS at the trusted TLS termination/web-server layer (or central app layer if appropriate), initially with a conservative max-age; do not enable `includeSubDomains` or preload until every covered hostname is verified HTTPS-capable.
  - **Header consistency gap:** `gallery_b2_diagnostic.php` and `gallery_b2_settings.php` emit some defensive headers again, but the Gallery settings page does not independently emit `X-Frame-Options` / `Permissions-Policy` / CSP; it currently inherits them from bootstrap. `app/Gallery/SecurePage.php` and `gallery_b2_diagnostic.php` emit a second CSP in addition to the central CSP. Browsers enforce multiple CSP policies cumulatively, which can cause functional restrictions (for example, Gallery's `blob:` image allowance is not present in the central policy); reconcile to one centrally generated, route-aware policy during CSP remediation. The diagnostic/settings pages inherit baseline clickjacking protections from bootstrap when the bootstrap reaches its normal header-emission stage.
  - **Ordering note:** the bootstrap's lock-vault POST handling and several redirect branches occur before its common security-header block. Those early redirect responses may therefore omit the baseline response headers; move common header emission earlier in the bootstrap as part of remediation, while preserving the HTTPS rejection and session initialization order.
  - No production headers, TLS configuration, or application code were changed. No live response/header test or production proxy configuration was available in this repository-only audit; actual deployed TLS/HSTS behaviour remains unverified.

- [x] **3.2** Review password authentication, password recovery, throttling, and 2FA.
  - Reviewed `app/Auth/AuthFlow.php`, `app/Security/SecurityBootstrap.php`, `private_data/vault_engine.php`, `private_data/email_template.php`, `diagnostics/copy-code.php`, and the login/recovery branches in `index.php` on `main`.
  - Password-based unlock uses the Argon2id-derived wrapping key to unwrap the 32-byte Vault Master Key, then AES-256-GCM to decrypt the vault. The current KDF metadata uses Argon2id13 with opslimit 3 and memlimit 32 MiB; the envelope reader enforces a minimum KDF cost. Passwords are not stored as plaintext or verified through a separate password-hash database.
  - **Confirmed authentication/throttling defect:** `AuthFlow.php` expects `vault_unlock($password)` to return `false` for an incorrect password and increments the `master` throttle only in that branch. However, `private_data/vault_engine.php::vault_unlock()` throws `RuntimeException` when password key-unwrapping or authenticated decryption fails. The password-login call is not wrapped in `try/catch`, and the bootstrap's global exception handler converts the exception into a generic HTTP 500 and exits. Therefore an ordinary incorrect password does not reach `sentryiq_throttle_failure('master', ...)`; the intended five-failures-per-15-minutes / 15-minute lockout is bypassed for the primary password path, and the user receives a server-error response instead of the normal invalid-password flow. **Risk: High**, because the principal online password-guessing control is ineffective. Remediation: normalize expected credential mismatch to a non-exception result at the authentication boundary (while preserving exceptions for storage/configuration faults), increment the throttle on every failed password attempt, and add tests proving wrong passwords return the normal failure response and lock out after the configured threshold.
  - Recovery-key flow does catch exceptions from envelope read/unwrapping, applies a five-failures-per-15-minute per-IP throttle, clears that throttle after success, and only authenticates after the recovery key unwraps the VMK and the encrypted records successfully decrypt. Recovery material is generated as 32 random bytes (256 bits) and normalized to 64 hexadecimal characters; its VMK wrapper uses the vault's Argon2id KDF and AES-256-GCM. Successful recovery calls `sentryiq_mark_authenticated()`, which regenerates the session ID and rotates the CSRF token.
  - 2FA uses a cryptographically random six-digit code, a 300-second pending-auth window, a 256-bit one-time copy-code bearer token, and a `hash_equals()` comparison. The copy-code endpoint atomically renames the token file before reading it and deletes the claimed file in `finally`, preventing a second successful consumption. Token files are created with exclusive mode and owner-only permissions. Successful completion regenerates the session ID, clears pending authentication values, and rotates the CSRF token.
  - **Throttle robustness findings:** the primary password throttle is keyed only by `REMOTE_ADDR`; this is a reasonable conservative source for the current code because `get_visitor_ip()` does not trust arbitrary forwarded headers, but deployments behind a shared reverse proxy may cause users to share one bucket unless a trusted-proxy design is explicitly configured. Throttle read/modify/write is not protected by a single shared lock: `LOCK_EX` is applied only to each unique temporary-file write, so concurrent failed requests can race and overwrite each other's counters. The throttle file also has no demonstrated pruning/size bound for distinct source IPs. These are resilience/hardening issues; the exception mismatch above is the primary confirmed defect.
  - **2FA send-rate limitation:** the master-password throttle is cleared immediately after a correct password, before sending the email challenge. There is no separate cooldown/limit for sending 2FA emails, so anyone who knows the password but cannot complete email verification can repeatedly trigger email sends. Add a distinct challenge-send throttle/cooldown and test it without weakening password retries.
  - Pending authentication expires after five minutes; 2FA verification is additionally limited to five failures per IP in a 15-minute window and tracks attempts in the session. On a blocked 2FA request the pending session values are cleared. The recovery flow uses a separate per-IP throttle. The 2FA code is stored in the session and in a short-lived private token file for the copy link; no password or plaintext vault contents are written by the reviewed login flow.
  - **Test status:** source-level audit only. No live mail delivery, production login, concurrency/rate-limit test, or automated authentication integration test was run in this item. Add regression tests for incorrect password handling/throttle, concurrent throttle updates, 2FA resend cooldown, expiry, five-attempt lockout, one-time copy token replay, recovery-key success/failure, and session/CSRF rotation before remediation is accepted.
  - No application code, credentials, email settings, or production configuration were changed.
- [x] **3.3** Review WebAuthn/passkey registration, authentication, challenge validation, and origin/RP binding.
  - Reviewed `app/Auth/PasskeyAuth.php`, `app/Auth/GalleryPasskeyAuth.php`, `app/Auth/PasskeyLogin.php`, `app/Auth/PasskeySetup.php`, `app/Auth/Passkeys.php`, and the central session/authentication helpers in `app/Security/SecurityBootstrap.php` on `main`.
  - Primary vault passkey flow derives the expected HTTPS origin and RP ID from the configured HTTPS `base_url`; validates exact `clientDataJSON.type`, origin, challenge using `hash_equals()`, and rejects `crossOrigin`; validates the RP ID hash in authenticator data; requires both user-presence and user-verification flags; checks ES256/P-256 public key type; verifies assertion signatures with OpenSSL; checks signature counters when both old/new counters are non-zero; and unwraps the vault master key only after assertion validation. Registration/deletion require authenticated vault state and CSRF. The final registered passkey cannot be removed. Passkey storage is written using exclusive temporary files, owner-only permissions, and rename.
  - **Confirmed registration key-binding gap:** `PasskeyAuth.php::pk_auth_data()` parses the attested credential ID from registration authenticator data but does not parse the CBOR `credentialPublicKey` embedded in that same authenticator data or compare it with the separate `publicKey` value submitted by the browser. The server validates that the submitted public key is a P-256 EC key, then stores it as the credential verification key. Thus the server does not establish that the stored verification key is the key the authenticator actually attested in the registration response; a modified registration request can pair the accepted credential ID/authenticator data with a different attacker-chosen P-256 key. Registration is already authenticated and CSRF-protected, so this is not an unauthenticated account takeover, but it weakens the binding/persistence guarantee of the passkey enrollment. **Risk: High for enrollment integrity/persistence.** Remediation: parse and validate the credential public key from attested credential data (including its CBOR structure and algorithm), compare it byte/semantically with the submitted key or remove the separate client-supplied key entirely, and add negative tests for mismatched keys and malformed CBOR.
  - **Challenge lifetime gap in primary vault passkeys:** registration and login options create 32-byte random challenges in the session, but neither stores a creation timestamp nor checks challenge age when the response is submitted. The browser's 60-second WebAuthn timeout is client-side and is not a server-side expiry control. Challenges are cleared on successful completion, but failed responses do not consume them. This differs from `GalleryPasskeyAuth.php`, which stores `gallery_passkey_challenge_at` and rejects assertions older than 120 seconds. Add server-side timestamps and strict expiry for primary registration and login challenges; clear them on expiry and after terminal attempts.
  - Gallery passkey flow is separately gated by an authenticated vault session. It derives exact HTTPS origin/RP ID from configured `base_url`, uses 32-byte session challenges with a 120-second server-side expiry, validates `webauthn.get`, origin, challenge, cross-origin flag, RP ID hash, UP/UV flags, ES256 signature, and authenticator counter. It binds subsequent Gallery-key initialization/add-credential operations to the just-verified credential ID and a five-minute verification window. Gallery credential-envelope retrieval also requires the authenticated session. No equivalent public/unauthenticated Gallery passkey operation was identified in the reviewed flow.
  - Primary vault passkey login options and assertion POST intentionally do not require CSRF because they form an unauthenticated WebAuthn login ceremony bound to a session challenge, exact origin/RP ID, and authenticator signature; registration and deletion are authenticated state changes and do require CSRF. This is consistent with the separate CSRF findings already recorded under 2.4.
  - **Test status:** no dedicated primary or Gallery WebAuthn server-side regression test was found in the repository test tree. This item is a source-level audit; no live authenticator/browser ceremony was performed. Required tests: valid and invalid origin/RP hash, challenge mismatch/expiry/replay, missing UP/UV, signature mismatch, counter rollback, duplicate credential, registration key mismatch/malformed CBOR, CSRF on register/delete, and Gallery verification-window expiry.
  - No application code, passkey credentials, or production configuration were changed.
- [x] **3.4** Review session creation, rotation, expiry, fixation protection, and logout/lock behaviour.
  - Reviewed `app/Security/SecurityBootstrap.php`, `app/Auth/AuthFlow.php`, `index.php`, passkey login/management entrypoints, first-run setup, `.user.ini`, and the session-related call sites in the root application routes on `main`.
  - Session startup is centralized in `sentryiq_security_bootstrap()`. It enables strict session ID mode and cookie-only sessions, configures Secure, HttpOnly, SameSite=Strict, path `/`, and a browser-session lifetime (`lifetime` 0), then starts the session. No explicit cookie domain is set, so the cookie is host-only. `.user.ini` does not override session settings or define a custom `session.gc_maxlifetime`.
  - Successful full authentication (password + email 2FA, recovery-key recovery, or passkey login) funnels through `sentryiq_mark_authenticated()`, which validates the 32-byte VMK, calls `session_regenerate_id(true)`, records username/authenticated_at/last_activity, clears pending-auth values, and rotates the CSRF token. This is the primary session-fixation control at the privilege transition. Strict mode also rejects uninitialized attacker-supplied IDs.
  - Idle timeout is 900 seconds. Each bootstrap-protected request with a master key checks `last_activity`; on expiry it clears the session, expires the cookie, destroys the session, and returns from the bootstrap. Otherwise it updates `last_activity`. Fresh-auth operations require an authenticated session whose `authenticated_at` is no more than 300 seconds old; the timestamp is set at full authentication and is not silently refreshed by ordinary activity. Re-unlock is required to regain the five-minute fresh-auth window.
  - Lock/logout is POST + CSRF protected in the central bootstrap, clears `$_SESSION`, expires the current session cookie using its active path/domain/Secure/HttpOnly attributes, and destroys the active session. The primary index contains a duplicate lock handler after the bootstrap, but the bootstrap handler redirects/exits first for matching POST requests. The deletion cookie omits an explicit SameSite attribute; cookie deletion is keyed by name/path/domain, so this does not appear to prevent invalidation, but the deletion options should be kept aligned with the configured cookie policy.
  - **Residual lifetime gap:** there is no absolute maximum lifetime for an authenticated session. A continuously active session can remain authenticated indefinitely because only the 15-minute idle timeout is enforced. Decide and document whether this is acceptable for the threat model; otherwise add a maximum authenticated age (separate from the 5-minute fresh-auth window) and test forced reauthentication.
  - **Route-enforcement dependency:** when the idle timeout expires, the bootstrap destroys the session and returns to its caller rather than terminating the request itself. `index.php` then renders the locked/login state, and protected handlers are expected to call `sentryiq_require_auth()` / `sentryiq_require_fresh_auth()` after bootstrap. This is not independently classified as a bypass here because the route-by-route authorization audit is item 3.5; it is an important invariant to verify there.
  - Pending 2FA state has a 300-second age check. `sentryiq_clear_pending_auth()` clears pending key/code/token/session fields; the final authentication helper clears them again when rotating the session. CSRF tokens are 256-bit random values and rotate after successful authentication. Lock destroys the session rather than merely removing the master key.
  - **Test status:** no dedicated session lifecycle/fixation/idle-timeout/absolute-age regression test was found in the repository test tree. Source-level review only; no live browser cookie/session test was run. Required tests: strict-mode/cookie attributes, ID changes after password+2FA/recovery/passkey auth, old ID invalidation, CSRF rotation, 15-minute idle expiry, five-minute fresh-auth expiry, POST+CSRF lock/logout, and behaviour of each protected route after bootstrap expires the session.
  - No application code, PHP configuration, or production session state was changed.

Gallery pages and storage authorization require authentication; POST storage actions validate the session CSRF token. B2 credential save/disconnect require fresh authentication and CSRF.   - **Sensitive-operation hardening gap:** primary passkey registration and deletion require an authenticated session and CSRF but do not call `sentryiq_require_fresh_auth()`. Adding/removing a credential changes the account's authentication boundary and should require the same five-minute fresh-auth gate used for B2 credential changes and system configuration. Risk is elevated if an authenticated browser session is hijacked. Remediation: require fresh authentication for register/delete and add tests for stale authenticated sessions. The Gallery passkey recovery-envelope GET also returns encrypted private/recovery-key envelopes to any authenticated session; assess whether fresh authentication should be required before returning those recovery materials.

The `.htaccess` rewrite map does not block direct requests under `/app/`. A direct request does not inherit the parent `index.php` variables, and no direct private-record disclosure was established in this review, but the templates can be executed/rendered as standalone PHP endpoints and unnecessarily expose internal UI structure. Add an explicit include-only guard (or move templates outside the document root) and verify direct HTTP requests are denied while normal inclusion still works. Other public static pages/endpoints noted above are intentionally public or separately gated.
  - `StorageAuthorization.php?action=cleanup_pending` is GET but only enumerates stale pending objects and returns short-lived signed DELETE URLs; it does not itself delete objects or mutate the object-store index. Actual commit/delete/cancel state changes are POST + CSRF. No new state-changing GET bypass was confirmed in this review.
  - **Authorization model:** the application is a single-vault/single-owner model; no multi-user role/tenant authorization layer was found or expected. The effective privilege boundary is the authenticated vault master-key session. The `require_auth` helper checks for a 32-byte session master key; full authentication helper sets it only after password+2FA, recovery-key recovery, or passkey verification and regenerates the session ID.
  - **Test status:** source-level route/handler audit only. No automated unauthenticated-vs-authenticated matrix was run across every route. Add integration coverage for all direct endpoints, stale-session behavior, CSRF rejection, passkey register/delete freshness, and read/write access to Vault, documents, Gallery objects, logs, update application, and diagnostics.
